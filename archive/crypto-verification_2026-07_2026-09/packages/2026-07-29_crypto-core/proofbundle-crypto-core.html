03Why the tests can't be satisfied by broken code

A library-backed implementation is verified by comparing against the library. With no library, correctness has to come from somewhere else — properties that only a correct implementation can satisfy.

The NTT is checked against an independent computation of the same product. Polynomial multiplication in Z_q[X]/(X²⁵⁶+1) is computed twice: once through the forward NTT → pointwise multiply → inverse NTT path, and once by direct schoolbook convolution with the X²⁵⁶ = −1 reduction applied by hand. These share no code. A wrong zeta table, a wrong rotation offset, or a wrong (2x+3y) mod 5 permutation breaks the agreement immediately.
  • NTT invertibility — forward then inverse returns the input exactly, across three seeds.
  • Encaps/decaps agreement — the shared secret derived by the sender matches the one recovered by the receiver, for all three parameter sets.
  • Implicit rejection — flipping a single ciphertext bit routes decapsulation to the J(z ‖ c) branch and yields a different secret, never the real one.
  • Determinism — identical seeds produce byte-identical keys and ciphertexts.
  • Size conformance — encapsulation key, decapsulation key and ciphertext lengths match the published tables.

For Keccak, node:crypto is used as an independent yardstick — but only inside the test file, never imported by the implementation. Three FIPS 202 known-answer values are additionally hardcoded, so the suite does not rest solely on Node agreeing with itself.

04The Keccak permutation

Twenty-four rounds of theta, rho, pi, chi, iota over a 25-lane state of 64-bit words.

export function keccakF1600(A) {
  for (let round = 0; round < 24; round++) {
    // theta
    for (let x = 0; x < 5; x++)
      C[x] = A[x] ^ A[x+5] ^ A[x+10] ^ A[x+15] ^ A[x+20];
    for (let x = 0; x < 5; x++)
      D[x] = C[(x+4) % 5] ^ rotl64(C[(x+1) % 5], 1);
    for (let y = 0; y < 5; y++)
      for (let x = 0; x < 5; x++) A[x + 5*y] ^= D[x];

    // rho (rotate lanes) + pi (permute positions), combined
    for (let y = 0; y < 5; y++)
      for (let x = 0; x < 5; x++)
        B[y + 5*((2*x + 3*y) % 5)] = rotl64(A[x + 5*y], ROT[x + 5*y]);

    // chi
    for (let y = 0; y < 5; y++)
      for (let x = 0; x < 5; x++)
        A[x + 5*y] = B[x + 5*y] ^
          ((~B[((x+1) % 5) + 5*y] & MASK64) & B[((x+2) % 5) + 5*y]);

    // iota
    A[0] ^= RC[round];
  }
  return A;
}

05Roots of unity, derived not transcribed

Reference implementations ship a hardcoded table of 128 zeta values. A single transcription error there corrupts the transform silently. These are computed at module load from ζ = 17 mod 3329: 

const ZETAS  = new Int32Array(128);
const GAMMAS = new Int32Array(128);
for (let i = 0; i < 128; i++) {
  ZETAS[i]  = powMod(ZETA, bitRev7(i), Q);
  GAMMAS[i] = powMod(ZETA, 2 * bitRev7(i) + 1, Q);
}

06Decapsulation, including the rejection branch

const KBar   = shake256(concat(z, c), 32);   // computed unconditionally
const cPrime = kpkeEncrypt(ek, mPrime, rPrime, p);

// difference accumulated without early exit
let diff = 0;
if (cPrime.length !== c.length) diff = 1;
else for (let i = 0; i < c.length; i++) diff |= cPrime[i] ^ c[i];

return diff === 0 ? KPrime : KBar;

K̄ is derived whether or not it is needed, and the comparison never short-circuits — both required so timing does not leak whether the ciphertext was valid.

ML-KEM reference vectors via Codespace—ABANDONED
On the abandoned row. The original plan generated ML-KEM test vectors from a reference library inside a GitHub Codespace. That was a dependency — even used only for verification — and was cut. Correctness is now established from algebraic identities instead, which requires no external code at all. The gh codespace scope blocker became irrelevant.
What these tests do not establish. The algebraic properties above catch implementation errors, not spec divergence. An implementation could be internally consistent and self-inverting while disagreeing with NIST's byte-level output. Closing that gap requires the published FIPS 203 known-answer vectors — static numbers from the standard document, not a library — or formal proof against the specification. Neither is done yet, and nothing here should be described as NIST-conformant until one of them is.
