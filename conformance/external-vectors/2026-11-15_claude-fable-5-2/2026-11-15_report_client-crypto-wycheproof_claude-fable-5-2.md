## What was run

The harness `2026-11-15_client-crypto_wycheproof-harness.mjs` (sha256 295e0ee5…1884) cuts the block between `PB NATIVE CRYPTO START` and `PB NATIVE CRYPTO END` out of a client build, evaluates it without a DOM, and runs the modules against expectations written by other parties: C2SP Wycheproof at commit 65ca494727a52944c204441c860b039e6786b99b (2026-11-11), the BLAKE3 team's test_vectors.json (sha256 dcb91ea8…f624), and OpenSSL through node:crypto. On every case OpenSSL can evaluate it runs as a second implementation, so an adapter fault would show as OpenSSL disagreeing with the vectors as well. 67 vector files, 13,983 cases: Ed25519, ECDSA P-256/P-384/P-521 in DER and IEEE P1363, RSA-PSS 2048/3072/4096 with SHA-256/384/512, X25519, ChaCha20-Poly1305, AES-256-GCM, HKDF-SHA-256, HMAC over SHA-2 and SHA-3, PBKDF2, ML-KEM-512/768/1024 (keygen, encapsulation, decapsulation), ML-DSA-44/65/87 (verify, signing from seed, signing from expanded key, through the message entry and the external-mu entry), BLAKE3, and sixteen digest and XOF functions on 314 input lengths each.

## Results

Attached build 7602f2aa (cloud, node 22.23.4, OpenSSL 3.5.9) and home build 2047b90c (pb7700k, node 24.19.0, OpenSSL 3.5.7) carry the identical native crypto block, sha256 f4bc8b965142a7b1…, so the 2,008-byte difference between those two same-named files lies outside the crypto. Both give 13,864 agreements and 119 disagreements; OpenSSL disagrees on none. All 119 are in ECDSA verification of DER-encoded signatures: 41 on P-256, 41 on P-384, 37 on P-521, every one a case Wycheproof marks invalid that the client accepts. They are BER and malformed encodings of a correct (r, s): long-form or non-minimal lengths, lengths that disagree with the content, overflowing lengths, indefinite length, integers with superfluous leading zeros, bytes appended after the SEQUENCE. Cause: `decode_der` in crypto/ecdsa.mjs reads the SEQUENCE length without checking it, reads INTEGERs without minimality or sign checks, and ignores trailing bytes, so many byte strings decode to one valid signature. No forgery follows, since the curve equation still has to hold for (r, s); the defect is signature malleability. In this system a signature's bytes are hashed into envelopes, lineage and Merkle leaves, so one signing event can be presented under several distinct hashes. The P1363 path, Ed25519 (including low-order and non-canonical cases), RSA-PSS, X25519, both AEADs, HKDF, HMAC, PBKDF2, ML-KEM, ML-DSA, BLAKE3 and every digest agree with the vectors on every case run.

## The candidate

`2026-11-15_strict-der.js` (sha256 e96431f5…48d8) replaces `decode_der` with a decoder that requires definite minimal lengths, minimal positive INTEGERs, and an exact end at the SEQUENCE boundary. `2026-11-15_apply-strict-der.py` (sha256 a7d8d86a…151e) writes a new file with that one function replaced and never writes its input. Applied to 7602f2aa it gives e2f82bf475c600b1…34a3; applied to 2047b90c it gives c1d85fd6225f09dd…7a9e. Both candidates carry the same native block, 63229d593429da56…, and both give 13,983 agreements and 0 disagreements on the full vector run. The 7602f2aa candidate was also run through the project's own Node runner (run_definition_node.mjs with extract_core.mjs from the 2026-11-02 provenance archive, whose extract of 7602f2aa matched the archive's pb_core_extract.js line for line) against conformance_1_0_0.json (sha256 256de0b9…): 17,822 of 17,822, the same as the unmodified build. No original build was modified. The ECDSA signer already emits strict DER, so the change touches only what verification admits.

## Limits of this run

The harness is a file written in this session, so its adapters are self-written; the guard against that is OpenSSL agreeing with the vectors on the same adapters, which it did on every case it could evaluate. ML-KEM, ML-DSA signing and BLAKE3 have no second implementation wired. Wycheproof has no SHA-3 HMAC truncation edge cases beyond its standard files, no Poly1305-only or BLAKE2 files, and the AES-GCM groups with 128- and 192-bit keys or non-96-bit nonces fall outside the module and were counted only as refusals. PBKDF2 cases above 20,000 iterations (one case) were skipped. No timing or constant-time analysis was attempted; the module headers already declare variable-time BigInt arithmetic as an open obligation. ~/src/proofbundle/proofbundle.html (b264c51a…) was not run: it uses a different module layout.
